# VAtlassian architecture audit — 2026-09-07

> This is the spec the P0 correctness plan implements. It is the user's audit,
> recorded verbatim in structure so the plan can argue from it.

VAtlassian can support signed, tamper-evident records within Atlassian, but asynchronous drift
detection cannot guarantee immediate locking or literal zero drift. For that guarantee, protect the
signed issue *before* edits occur and stage proposed changes separately until they are signed.

## Operating model decision (2026-09-07)

Three options were offered. **Chosen: strict mode as an opt-in policy.**

```
policy.mode = 'STRICT' | 'DETECT'

STRICT: preconditions validated at setup (editable=false present,
        write identity proven) else configuration REFUSED
DETECT: current model, all audit defects fixed

Shared: adapters, operation states, one signature resolver, verification.
```

Delivery is sliced into three plans, each shipping working software:

| Plan | Covers |
|---|---|
| **Plan 1 — P0 correctness** (`2026-09-07-p0-correctness.md`) | Defects that are wrong under *both* operating models |
| Plan 2 — locking architecture | `STRICT`/`DETECT` policy, proposal snapshots, durable operation states, one signature resolver |
| Plan 3 — compliance & performance | Part 11 controls, batching, resumable background execution, AI evidence |

## Locking needs a precise enforcement boundary

Jira workflow validators reject transitions; they do not intercept ordinary field edits. Workflow
properties such as `jira.issue.editable=false` restrict editing at a status. Issue properties are
mutable metadata, not access controls.

Two workable operating models:

- **Strict zero drift:** Keep signed Jira records protected. Store proposed changes as Forge
  snapshots. Reviewers sign the proposed snapshot; an authorized execution path applies it and
  verifies it. Rejection discards the proposal because Jira's approved values never changed.
- **Editable issues with drift review:** Allow edits, detect them asynchronously, then restrict
  further activity. This supports restoration, but there is an unavoidable exposure window. It
  cannot satisfy an absolute immediate-lock promise.

The requirement that *no state change occurs without a signature* also rules out an unsigned
automatic move to "Under Review." Under the strict interpretation, set the app's incident state
without changing Jira status and keep the existing Jira restrictions in force.

Validate the chosen write identity against those restrictions. Do not solve restoration by giving
every reviewer Jira administrator privileges. Administrator workflow changes and other privileged
writers remain part of the controlled operating environment.

## Transition coverage must be configured and proven in both systems

Store a versioned policy containing project, issue type, workflow, transition ID, source/destination
statuses, required reviewer role, signature policy and tracked-field configuration version.

Require:

1. The VAtlassian validator on the **published Jira transition**.
2. A matching enabled Forge policy.
3. A valid signature authorization bound to that exact transition and reviewed snapshot.

Use transition IDs, not merely source/destination pairs: two transitions can share the same
endpoints. Reconcile published workflow configuration after changes and periodically.

After a transition, correlate it with a recorded authorization and execution operation. An unexpected
transition produces a durable incident containing actor, time, statuses and available
transition/changelog identifiers. Ambiguous evidence must remain unresolved; do not infer
authorization from a nearby signature.

Mirror only a small display object into an issue property:

```json
{
  "state": "DRIFT",
  "baselineVersion": 12,
  "incidentId": "incident-123",
  "operationState": "BLOCKED"
}
```

The authoritative state belongs in Forge storage. A property alone does not render a banner or
guarantee placement at the top of Jira's issue view. Use the supported issue panel/context surfaces
and make their status prominent.

## Restoration: versioned snapshots and explicit field adapters

Each baseline should retain:

- Every configured field ID, its schema and adapter version.
- Its complete raw value, including explicit `null` and empty arrays.
- A cryptographic digest of the preserved value.
- The frozen field-set/configuration version.
- Tenant/issue identity, capture time, signature linkage and previous-baseline reference.

Keep **integrity comparison** separate from **semantic presentation**. A semantic diff may summarize
formatting changes; it must not make them disappear from integrity checks or restoration.

For hashing, canonicalize object-key ordering while preserving meaningful array order and ADF
structure. Distinguish an unreadable/missing field from a captured null. Store hashes **and values**:
hashes cannot reconstruct content.

Use an adapter registry:

| Field family | Restore representation |
|---|---|
| Description, environment, textarea custom fields | Full ADF document object; preserve nodes, marks and attributes |
| Plain text, numbers, dates | Validated primitive in the field's accepted format |
| Users and multi-users | `{accountId}` or arrays of those objects |
| Selects, versions, components | Stable IDs in the appropriate object/array structure |
| Cascading select | `{id, child: {id}}`, preserving both selections |
| Status, links, parent, app-owned fields | Explicit supported handler and permission checks |

Jira REST v3 accepts ADF for description, environment and textarea custom fields; a generic
string-schema conversion is insufficient.

For each rejection:

1. **Preflight all tracked fields.** Verify retained values and digests, current field contexts,
   supported operations, referenced options/users and write permissions.
2. **Capture the rejected candidate** so restoration never erases the evidence of what was rejected.
3. **Obtain and persist the rejection signature**, bound to the candidate, original baseline and
   exact restoration plan.
4. **Claim the operation** using a conditional version update and unique operation identifier.
5. **Apply ordinary fields together** in one issue update. Run necessary special handlers as recorded
   steps.
6. **Read every tracked field back** and compare against the original baseline.
7. Declare completion only when the entire tracked projection matches. Otherwise retain
   `RESTORE_FAILED` or `RESTORE_PARTIAL` and keep restrictions active.

"All custom fields" cannot be an unconditional promise: calculated/read-only fields, deleted options
and third-party fields without supported write APIs may be impossible to restore exactly. Reject
unsupported configurations at setup for strict mode. If capabilities change later, preserve the
incident and require controlled remediation.

## Both buttons enter one server-owned signature flow

The browser should only choose the decision and collect signature input:

```tsx
<Button onClick={() => openSignature("APPROVE")}>Approve</Button>
<Button onClick={() => openSignature("REJECT")}>Reject</Button>
```

Opening the dialog should request a server-created, expiring challenge bound to:

```text
tenant + issue + signer + decision + meaning
baseline ID/version/hash + candidate snapshot hash
field configuration version + transition ID + operation-plan hash
nonce + expiry
```

After confirmation, the UI submits the challenge ID and signature credentials to **one resolver**.
That resolver must:

1. Derive identity from trusted Forge context and recheck eligibility.
2. Load the challenge and immutable snapshots from server storage.
3. Verify the configured electronic-signature workflow without fallback.
4. Reject stale content, changed policy, expired challenges and replay.
5. Persist signature evidence and a durable execution operation.
6. Execute promotion or restoration only through that operation.
7. Verify the outcome before publishing completion.

For approval, promote **the snapshot the reviewer signed**, never an arbitrary fresh read. If
transition screens or post-functions produce different tracked content, keep the operation blocked
and obtain a new review.

Retries may resume the same signed operation only when its target and permitted intermediate state
remain valid. They must not replace a signed content hash with today's hash. The current retry path
does exactly that substitution and should be redesigned. `src/usecases/restore.js:22`.

Use conditional updates, unique operation keys and recoverable execution steps. A database claim does
not make Jira REST calls and Forge storage one atomic transaction.

## Performance and zero egress

- Read the configured field set together; avoid one Jira request per field.
- Batch snapshot persistence and retain large values in validated chunks.
- Use one multi-field update and one full verification read where possible.
- Move long restoration, attribution and AI work into resumable background execution.
- Honor `Retry-After`; persist failures and reconcile missed work. Forge supports explicit event
  retry requests — the current swallowed errors do not request them.
- Load field differences and ADF rendering progressively. Keep hashing, integrity decisions and
  validator checks independent of AI.
- Populate "My Approvals" from indexed incident/operation records and enforce both reviewer
  eligibility and Jira visibility.

Use Atlassian-hosted Forge LLMs for summaries; the manifest already declares that capability.
Generate summaries from frozen diff evidence, retain model/prompt versions and source references, and
label them as AI-generated. Preserve deterministic Who/What/When evidence separately. Event arrival
time is not necessarily edit time, and a fresh read cannot reconstruct every intermediate ADF
revision.

Strict zero egress should exclude external analytics as well as external AI and storage. The Runs on
Atlassian badge allows limited analytics exceptions, so badge eligibility alone is weaker than this
requirement.

## 21 CFR Part 11

Part 11 compliance requires validated controls and operating procedures beyond hashing. Establish
intended-use validation; access and authority checks; retained, timestamped audit trails; complete
human-readable and electronic exports; signer name, execution time and meaning; and permanent
signature-to-record linkage. Identity verification, credential recovery, training, change control and
applicable FDA electronic-signature certification also need documented ownership.

An existing Atlassian session plus TOTP should not automatically be declared compliant: validate its
identification components and controlled-session behavior against §11.200. A hash chain provides
tamper evidence within its trust boundary; it does not prevent a privileged app operator from
rewriting records and recomputing hashes. Retention and privileged-change controls must address that
boundary.

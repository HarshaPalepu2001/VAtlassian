# Building Forge Signature

**Decision recorded:** Forge-only. No external backend, no remotes, no egress.
**Date** 8 August 2026 · **Supersedes** the Option B connector spec earlier in this thread.

---

## 0. What changes, and what it costs

This reverses the Option B lock in the project memory. The benefits and costs are listed below.

**What you gain**

- **Runs on Atlassian eligibility.** Zero egress is the whole requirement. For regulated buyers this removes an entire vendor security review, and it is the strongest commercial argument for the reversal.
- No infrastructure to run, secure, certify or bill for. No separate SOC 2 to fund; the product relies on Atlassian's.
- No data residency engineering. Forge SQL is provisioned per installation inside Atlassian's estate.
- A much shorter path to a first Marketplace listing.

**Costs to discuss with Ramkumar**

| Loss | Consequence |
| --- | --- |
| Real ACID transactions | Every multi-step write becomes a single-statement compare-and-swap. Solvable (§3.1), but it constrains every schema decision. |
| DB-level immutability (triggers, revoked grants) | Alteration is **detected, not prevented**. This is a smaller loss than it sounds: [§11.10(a)](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11/subpart-B/section-11.10) requires the "ability to **discern** invalid or altered records", which a hash chain satisfies literally. Part 11 nowhere requires WORM or object-lock storage. |
| Object storage with compliance-mode lock | No independent archival copy held by the app. Pressure on §11.10(c) retrieval-throughout-retention, answered by sealed Confluence export plus the customer's Atlassian retention SOP. See §4. |
| Unbounded storage | 1 GiB per production install, hard. The audit ledger is append-only and grows indefinitely, with roughly a 2–3 year ceiling for an active tenant (§3.3). |
| Codebeamer parity | ReqIF import, large baselines and full trace-graph queries are hard-to-impossible inside these limits. |

The scope is a Part 11 electronic signature product that runs entirely on Atlassian. It does not provide the full VAtlassian ALM platform. If the plan remains to replace Codebeamer, start with signatures and design the data export needed for a later migration from Forge SQL to an external backend.

## 0b. Authentication factor: TOTP, not PIN, not push (2026-08-18)

**Decision recorded.** The static PIN is replaced by TOTP codes (RFC 6238),
generated by Microsoft Authenticator or any equivalent authenticator app.
The distinction matters because push authentication conflicts with the no-egress decision in §0.

The ask was "rely on Microsoft Authenticator instead of a PIN." That is
ambiguous between two very different builds:

| Reading | What it requires | Runs on Atlassian |
| --- | --- | --- |
| **TOTP.** Microsoft Authenticator used as a standard 6-digit code generator, added as a generic "Other account" (identical in spirit to Google Authenticator) | A shared secret, encrypted at rest, and HMAC verification done entirely inside this Forge function. TOTP verification runs locally using the standard algorithm and makes no calls to Microsoft. | **Preserved.** No `remotes`, no egress. |
| **Push / Entra ID / PingID.** An "approve on your phone" prompt, or federated Microsoft sign-in | OAuth/Graph calls to `login.microsoftonline.com` (or PingID's API) at authentication time, a `remotes` block, external fetch permission, and the customer standing up their own Azure AD app registration or PingID tenant. | **Forfeited.** This reopens the "Option B" external-connector architecture §0 explicitly reversed away from. |

The choice is TOTP. It preserves zero egress, Runs on Atlassian eligibility and no external backend. The user opens Microsoft Authenticator and types a code. NIST SP 800-63B classifies the phone holding the secret as a possession factor, making it a better second identification component for §11.200 than a memorised PIN. HMAC verification avoids the "PBKDF2 cost inside a Forge function" latency risk recorded for PINs, retiring that Phase 0 risk in §7. `last_used_step` prevents code reuse, as described in `lib/totp.js`.

TOTP does not provide push notifications, biometric approval or integration with a customer's Entra ID tenant policy. If a design partner requires Microsoft push infrastructure or PingID, use the "Both — two editions" option recorded in the discussion. Ship the Runs-on-Atlassian TOTP edition first and scope a separate push edition with egress for later. Keep it outside V1 until requested.

## 1. Verified platform constraints

The following constraints came from Atlassian documentation checked when this reference was written. The design must fit them.

| Constraint | Value | Where it bites |
| --- | --- | --- |
| **One statement per SQL call** | No `;`-separated statements. No `BEGIN`/`COMMIT`. | No transactions. Drives the entire concurrency design. |
| Foreign keys | Not supported | Referential integrity is application-enforced |
| Storage per install | 1 GiB prod · 256 MiB staging · 128 MiB dev | Audit ledger ceiling |
| Tables | 200 max | Not binding |
| Row size | 6 MiB | Rules out blobs in-row at any volume |
| DML throughput | 150 requests/sec | Not binding at signature volumes |
| Query timeouts | `SELECT` 5s · `INSERT`/`UPDATE`/`DELETE` 10s · DDL 20s | Validator latency budget |
| Response size | 4 MiB | Audit exports must paginate |
| `SHA2()` in SQL | Triggers a policy audit; may be rejected or rate-limited | **Hash in Node, never in SQL** |
| `AUTO_INCREMENT` | Discouraged (hotspots) | Use `BINARY(16)` UUIDs or `AUTO_RANDOM` |
| Adding the `sql` module | Forces a major version upgrade + admin re-consent | Get the schema right before first publish |
| Schema application | Queued DDL executed by a **scheduled trigger**, not at install | Allow for schema application after installation |
| Dashboard modules, `global:ui`, Containers | **EAP** | Excluded by your standing rule |
| `jira:workflowValidator`, `personalSettingsPage`, Object Store | **Preview** | Acceptable; 1-month deprecation window |

## 3. The four hard problems

### 3.1 atomicity without transactions

Two operations must be atomic and neither can use a transaction.

Consume a signature with a single-statement compare-and-swap:

```sql
UPDATE va_signature
   SET state = 'CONSUMED', consumed_at = ?
 WHERE signature_id = ? AND state = 'PENDING' AND expires_at > ?
```

Check `affectedRows === 1`. Exactly one concurrent caller wins; the loser sees `0` and denies. Correct without any transaction, because a single UPDATE is atomic in the engine.

Appending to the audit chain requires a read followed by a write. Two concurrent appends could read the same tail hash and fork the chain.

Use `seq` as the primary key so uniqueness serializes appends.

```
read tail (seq = N, hash = H)
compute this_hash = SHA256(N+1 || H || canonical(event))
INSERT (seq = N+1, prev_hash = H, this_hash = ...)
  duplicate key -> someone took N+1; re-read and retry (bounded)
  success       -> appended
```

The primary key serializes writes without a transaction. Retry a bounded number of times. If the app cannot record the event, refuse the action.

### 3.2 the validator still cannot see the user

Unchanged by the architecture switch. Atlassian's documented lambda payload is `{ issue: { key }, configuration, transition }`. It has no user object and supplies only the mutable issue key. Expression validators see `user` but cannot reach storage.

The panel signs and the validator checks. A signature is created ahead of time in `PENDING` state, bound to a target status and a content hash; the validator resolves key → immutable numeric ID and consumes it.

**This is the #1 build risk.** The validator does a REST call plus two SQL round trips inside Jira's transition. If that exceeds Jira's validator timeout, the design fails. **Measure it in week 1, before building anything else.** That timeout is not documented and must be established empirically.

### 3.2b measured: append contention is O(N²)

Built and tested. 40 simultaneous ledger appends produce ~780 duplicate-key
collisions, with a mean of 20 attempts per writer and a worst case of N. Correctness holds (the
chain verifies, every writer succeeds, nobody is starved), but the aggregate
database work is quadratic, and Forge SQL caps DML at 150 requests/second per
install.

Not a problem at realistic volumes; a team signing 50–200 times daily will
rarely see two concurrent appends. It is the deciding input for one Phase 0
measurement: if burst concurrency exceeds ~10, move chain computation off the
write path (unchained insert with a self-hash, single scheduled sealer assigns
`seq` and links the chain. This takes O(N) instead of O(N²), but leaves a short window
in which deletion of an unsealed event is undetectable). Measure before changing.

### 3.3 storage ceiling

1 GiB, an append-only ledger, and no archival egress.

At roughly 1 KB per audit row, 1 GiB is about **1.05 million events**. A tenant running 200 signings/day at ~5 events each (context, attempt, sign, consume, close) produces ~1,000 events/day. The ceiling arrives in about 2.9 years. That is inside the retention period of every regulation you are targeting, so it belongs in V1, not V2.

Export sealed segments to Confluence periodically. A scheduled job packages a date-bounded, hash-sealed ledger segment, attaches it to the audit dossier page, verifies the attachment hash, and only then prunes the exported rows. Each segment carries the previous segment's terminal hash, so the chain stays continuous across the prune boundary. The design already includes Confluence for this purpose.

Confluence attachments also lack object lock. Export relieves the storage ceiling but does not resolve §11.10(c).

### 3.4 §11.300(d) alerting with zero egress

The clause requires detecting *and reporting, immediately and urgently*, attempted unauthorised credential use. No egress means no email, no webhook, no pager.

Use Jira notifications. On lockout, create a work item in a configured "Signature Security" project via `asApp()`. Jira's own notification scheme delivers it to the security group. The app does not send data outside Atlassian. Jira delivers notifications through a channel the customer controls and audits.

The alert enters the customer's existing incident workflow. This requires the `write:jira-work` scope.

## 4. Retention requirements

These retention limits do not block a compliant implementation, but they constrain its claims and require a documented customer SOP.

### What the regulation actually says

[§11.10](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11/subpart-B/section-11.10) opens: *"**Persons who use closed systems** to create, modify, maintain, or transmit electronic records shall employ procedures and controls…"* The obligation sits on the regulated company, not the software vendor. You supply capability and evidence; they achieve compliance. There is no such thing as a compliant product, only a compliant validated implementation. The assessor makes that determination.

Three clauses touch storage:

- §11.10(a) requires *"the ability to discern invalid or altered records."* The requirement is to detect alteration. The hash-chained ledger meets that requirement; the clause does not demand WORM storage.
- §11.10(b) requires the ability to *"generate accurate and complete copies… in both human readable and electronic form suitable for inspection, review, and copying by the agency."* Satisfied by the audit export (HTML dossier + machine-readable ledger segment).
- §11.10(c) and §11.10(e) require *"accurate and ready retrieval throughout the records retention period"*, and audit trail documentation *"retained for a period at least as long as that required for the subject electronic records."* These clauses require a retention procedure.

### Customer retention procedures

The regulated *system* is Jira + Confluence + this app, not this app alone. Jira stores the work item, Confluence stores the sealed dossier, and Forge SQL stores the signature and chain. All three sit inside the customer's Atlassian tenant and depend on its retention and backup procedures. A customer deploying this must have a Jira/Confluence retention SOP regardless of us.

The implementation must include:

- **Sealed export before prune.** A date-bounded ledger segment, hash-sealed, attached to the Confluence dossier, attachment hash verified, and only then are the rows pruned. Each segment carries the prior segment's terminal hash, so the chain stays continuous across the boundary.
- **A retention SOP template** shipped with the app, naming what the customer must configure: Confluence space permissions, deletion controls, backup policy, retention period.
- **A limitation statement.** the app holds no legal-hold-protected copy. A user with sufficient Confluence permissions can delete the dossier. That risk is managed by access control and procedure, exactly as it is in every database-backed ALM tool including Codebeamer.

### The engineering instruction that follows

**Build the export step behind an interface.** `ExportTarget` with one implementation (`ConfluenceTarget`) in V1. If retention ever needs object-lock storage, add `S3ObjectLockTarget` through that interface. The same interface supports a later migration to an external backend for broader ALM requirements.

| **3 · Compliance surface** | Hash-chained ledger + verification job, 3-attempt lockout, Jira-issue alerting, 90-day dead-credential check, self-service TOTP reset, My Signatures worklist, content-change review queue | 2.5 wks |
| **4 · Retention** | Sealed Confluence export + verified prune. Required to address the 1 GiB limit. | 1.5 wks |
| **5 · Hardening & evidence** | Fail-closed test matrix, chain verification tool, Part 11 conformance matrix, tool qualification pack, Marketplace security review prep | 3 wks |

**≈ 13 weeks to a defensible V1**, plus Marketplace review turnaround.

Complete Phase 0 before phases 1–5. If validator latency exceeds Jira's budget, revise the gate design first.

## 6. Refuse transitions on gate errors

One rule outranks every other design consideration: **any error, anywhere in the gate path, blocks the transition.**

SQL timeouts, key resolution failures, exhausted chain append retries, malformed rows and unexpected exceptions all return `{ result: false }` with an explanatory message. There is no code path in this app that permits a transition it could not affirmatively verify.

A validator that permits a transition on error silently bypasses the approval control and fails the audit requirement.

## 7. Open items

**Must resolve in Phase 0**

- Measure the undocumented Jira workflow validator timeout because the design depends on it
- ~~PBKDF2 600k iteration cost inside a Forge function invocation budget~~ retired: TOTP verification is a single HMAC-SHA1, not a deliberately-slow KDF (§0b)
- App-level encrypted variable provisioning for the TOTP secret key (`forge variables set --encrypt`). Confirm it is set before first enrolment, and design the "not yet configured" failure path (fail closed: no key, no enrolment, not "enrol with a weaker fallback")
- TOTP clock-drift window (`TOTP_WINDOW = 1`, ±30s) sufficiency against real user devices. Widen only if Phase 0 evidence shows genuine drift-caused failures, not speculatively
- Whether `write:jira-work` for security alerting AND rejected-change author notification passes the security review, given the app otherwise writes nothing

**Must resolve before launch**

- Break-glass override: an explicit, logged, time-boxed grant that the *consume* path reads. Never a branch in the validator, or the override is invisible to the chain.
- Confluence space and permission model for the audit dossier
- Retention SOP template drafted and reviewed with your first design partner before build completes
- Confirm no design partner is contractually required to hold legal-hold-capable storage (some pharma QMS agreements are)

# Forge Signature — What it takes to build

**Decision recorded:** Forge-only. No external backend, no remotes, no egress.
**Date** 8 August 2026 · **Supersedes** the Option B connector spec earlier in this thread.

---

## 0. What changes, and what it costs

This reverses the Option B lock in the project memory. Both halves of the trade are load-bearing, so both are stated up front.

**What you gain**

- **Runs on Atlassian eligibility.** Zero egress is the whole requirement. For regulated buyers this removes an entire vendor security review, and it is the strongest commercial argument for the reversal.
- No infrastructure to run, secure, certify or bill for. No SOC 2 of your own to fund — you inherit Atlassian's.
- No data residency engineering. Forge SQL is provisioned per installation inside Atlassian's estate.
- A much shorter path to a first Marketplace listing.

**What you give up — say these to Ramkumar, do not bury them**

| Loss | Consequence |
| --- | --- |
| Real ACID transactions | Every multi-step write becomes a single-statement compare-and-swap. Solvable (§3.1), but it constrains every schema decision. |
| DB-level immutability (triggers, revoked grants) | Alteration is **detected, not prevented**. This is a smaller loss than it sounds: [§11.10(a)](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11/subpart-B/section-11.10) requires the "ability to **discern** invalid or altered records", which a hash chain satisfies literally. Part 11 nowhere requires WORM or object-lock storage. |
| Object storage with compliance-mode lock | No independent archival copy held by the app. Pressure on §11.10(c) retrieval-throughout-retention, answered by sealed Confluence export plus the customer's Atlassian retention SOP. See §4. |
| Unbounded storage | 1 GiB per production install, hard. The audit ledger is append-only and grows forever — roughly a 2–3 year ceiling for an active tenant (§3.3). |
| Codebeamer parity | ReqIF import, large baselines and full trace-graph queries are hard-to-impossible inside these limits. |

**The honest framing:** this is a strong Part 11 *electronic signature* product that runs entirely on Atlassian. It is not the full VAtlassian ALM platform. If displacing Codebeamer is still the destination, this is a wedge — and the eventual migration from Forge SQL to an external backend is a data-export problem to design for now, not discover later.

## 0b. Authentication factor: TOTP, not PIN, not push (2026-08-18)

**Decision recorded.** The static PIN is replaced by TOTP codes (RFC 6238),
generated by Microsoft Authenticator or any equivalent authenticator app.
This was a real fork, worth writing down because the wrong reading breaks
everything in §0.

The ask was "rely on Microsoft Authenticator instead of a PIN." That is
ambiguous between two very different builds:

| Reading | What it requires | Runs on Atlassian |
| --- | --- | --- |
| **TOTP** — Microsoft Authenticator used as a standard 6-digit code generator, added as a generic "Other account" (identical in spirit to Google Authenticator) | A shared secret, encrypted at rest, and HMAC verification done entirely inside this Forge function. No call to Microsoft, ever — TOTP is a local, standards-based algorithm, not a live protocol. | **Preserved.** No `remotes`, no egress. |
| **Push / Entra ID / PingID** — a real "approve on your phone" prompt, or federated Microsoft sign-in | OAuth/Graph calls to `login.microsoftonline.com` (or PingID's API) at authentication time, a `remotes` block, external fetch permission, and the customer standing up their own Azure AD app registration or PingID tenant. | **Forfeited.** This reopens the "Option B" external-connector architecture §0 explicitly reversed away from. |

Chosen: **TOTP.** It keeps every load-bearing claim in §0 — zero egress,
Runs on Atlassian, no external backend — while still giving the customer the
literal experience of opening Microsoft Authenticator and typing a code. It
is also, on its own merits, a better second identification component for
§11.200 than a memorised PIN: TOTP is what NIST SP 800-63B calls a
possession factor (the phone holding the secret), it is not vulnerable to
the "PBKDF2 cost inside a Forge function" latency risk the PIN carried (HMAC
is cheap; that Phase 0 risk is retired, see §7), and codes cannot be reused
(replay-guarded by `last_used_step`, see `lib/totp.js`).

**What this does not give you:** push notifications, biometric approval, or
any integration with a customer's existing Entra ID tenant policy. If a
design partner insists on that specifically — not "an authenticator app,"
but genuinely Microsoft's push infrastructure or PingID — that is the
"Both — two editions" option raised in this thread: ship the Runs-on-
Atlassian TOTP edition as the flagship listing, and treat a push-based
egress edition as a separate, later, explicitly-scoped add-on. Do not build
it speculatively into V1.

## 1. Verified platform constraints

Every line below is from Atlassian's current documentation, checked today. These are the facts the design has to survive.

| Constraint | Value | Where it bites |
| --- | --- | --- |
| **One statement per SQL call** | No `;`-separated statements. No `BEGIN`/`COMMIT`. | No transactions. Drives the entire concurrency design. |
| Foreign keys | Not supported | Referential integrity is application-enforced |
| Storage per install | 1 GiB prod · 256 MiB staging · 128 MiB dev | Audit ledger ceiling |
| Tables | 200 max | Not binding |
| Row size | 6 MiB | Rules out blobs in-row at any volume |
| DML throughput | 150 requests/sec | Not binding at signature volumes |
| Query timeouts | `SELECT` 5s · `INSERT`/`UPDATE`/`DELETE` 10s · DDL 20s | Validator latency budget |
| Response size | 4 MiB | Audit exports must paginate |
| `SHA2()` in SQL | Triggers a policy audit; may be rejected or rate-limited | **Hash in Node, never in SQL** |
| `AUTO_INCREMENT` | Discouraged (hotspots) | Use `BINARY(16)` UUIDs or `AUTO_RANDOM` |
| Adding the `sql` module | Forces a major version upgrade + admin re-consent | Get the schema right before first publish |
| Schema application | Queued DDL executed by a **scheduled trigger**, not at install | Install is not instantly ready — design for it |
| Dashboard modules, `global:ui`, Containers | **EAP** | Excluded by your standing rule |
| `jira:workflowValidator`, `personalSettingsPage`, Object Store | **Preview** | Acceptable; 1-month deprecation window |

## 3. The four hard problems

### 3.1 Atomicity without transactions

Two operations must be atomic and neither can use a transaction.

**Consuming a signature** — single-statement compare-and-swap:

```sql
UPDATE va_signature
   SET state = 'CONSUMED', consumed_at = ?
 WHERE signature_id = ? AND state = 'PENDING' AND expires_at > ?
```

Check `affectedRows === 1`. Exactly one concurrent caller wins; the loser sees `0` and denies. Correct without any transaction, because a single UPDATE is atomic in the engine.

**Appending to the audit chain** — harder, because it is read-then-write. Two concurrent appends could read the same tail hash and fork the chain.

Solution: make `seq` the primary key and let uniqueness do the serialising.

```
read tail (seq = N, hash = H)
compute this_hash = SHA256(N+1 || H || canonical(event))
INSERT (seq = N+1, prev_hash = H, this_hash = ...)
  duplicate key -> someone took N+1; re-read and retry (bounded)
  success       -> appended
```

The primary key is the lock. No transaction needed. Retry is bounded and, on exhaustion, **fails the operation closed** — an event that cannot be recorded means the action must not be permitted.

### 3.2 The validator still cannot see the user

Unchanged by the architecture switch. Atlassian's documented lambda payload is `{ issue: { key }, configuration, transition }` — no user object, and only the *mutable* issue key. Expression validators see `user` but cannot reach storage.

So: **the panel signs, the validator only checks.** A signature is created ahead of time in `PENDING` state, bound to a target status and a content hash; the validator resolves key → immutable numeric ID and consumes it.

**This is the #1 build risk.** The validator does a REST call plus two SQL round trips inside Jira's transition. If that exceeds Jira's validator timeout, the design fails. **Measure it in week 1, before building anything else.** That timeout is not documented and must be established empirically.

### 3.2b Measured: append contention is O(N²)

Built and tested. 40 simultaneous ledger appends produce ~780 duplicate-key
collisions — mean 20 attempts per writer, worst case N. Correctness holds (the
chain verifies, every writer succeeds, nobody is starved), but the aggregate
database work is quadratic, and Forge SQL caps DML at 150 requests/second per
install.

Not a problem at realistic volumes; a team signing 50–200 times daily will
rarely see two concurrent appends. It is the deciding input for one Phase 0
measurement: if burst concurrency exceeds ~10, move chain computation off the
write path (unchained insert with a self-hash, single scheduled sealer assigns
`seq` and links the chain — O(N) instead of O(N²), at the cost of a short window
in which deletion of an unsealed event is undetectable). Measure before changing.

### 3.3 Storage ceiling

1 GiB, an append-only ledger, and no archival egress.

At roughly 1 KB per audit row, 1 GiB is about **1.05 million events**. A tenant running 200 signings/day at ~5 events each (context, attempt, sign, consume, close) produces ~1,000 events/day — **the ceiling arrives in about 2.9 years.** That is inside the retention period of every regulation you are targeting, so it belongs in V1, not V2.

**Answer:** periodic sealed export to Confluence. A scheduled job packages a date-bounded, hash-sealed ledger segment, attaches it to the audit dossier page, verifies the attachment hash, and only then prunes the exported rows. Each segment carries the previous segment's terminal hash, so the chain stays continuous across the prune boundary. Confluence is already in the stack for exactly this.

What this is not: Confluence attachments have no object lock either. It relieves the storage ceiling. It does not close §11.10(c).

### 3.4 §11.300(d) alerting with zero egress

The clause requires detecting *and reporting, immediately and urgently*, attempted unauthorised credential use. No egress means no email, no webhook, no pager.

**Answer: let Jira do the notifying.** On lockout, create a work item in a configured "Signature Security" project via `asApp()`. Jira's own notification scheme delivers it to the security group. We never egress; Jira does — through a channel the customer already controls and audits.

This is a better outcome than a bolted-on webhook, because the alert lands in the customer's existing incident workflow. Cost: one scope, `write:jira-work`.

## 4. Retention: the one clause under real pressure

**Verdict first: this does not block a compliant implementation.** It does constrain what you may claim, and it requires a customer SOP you must document rather than assume.

### What the regulation actually says

[§11.10](https://www.ecfr.gov/current/title-21/chapter-I/subchapter-A/part-11/subpart-B/section-11.10) opens: *"**Persons who use closed systems** to create, modify, maintain, or transmit electronic records shall employ procedures and controls…"* The obligation sits on the regulated company, not the software vendor. You supply capability and evidence; they achieve compliance. There is no such thing as a compliant product, only a compliant validated implementation — which is the assessor's determination, not ours.

Three clauses touch storage:

- **§11.10(a)** — *"the ability to discern invalid or altered records."* **Discern**, not prevent. The hash-chained ledger satisfies this on its face. This is the clause people wrongly cite to demand WORM storage.
- **§11.10(b)** — *"generate accurate and complete copies… in both human readable and electronic form suitable for inspection, review, and copying by the agency."* Satisfied by the audit export (HTML dossier + machine-readable ledger segment).
- **§11.10(c)** and **§11.10(e)** — *"accurate and ready retrieval throughout the records retention period"*, and audit trail documentation *"retained for a period at least as long as that required for the subject electronic records."* **This is the pressure point.**

### Why it is survivable

The regulated *system* is Jira + Confluence + this app, not this app alone. The work item lives in Jira, the sealed dossier in Confluence, the signature and chain in Forge SQL — all three inside the customer's own Atlassian tenant, all three already covered by whatever retention and backup posture that customer runs. A customer deploying this must have a Jira/Confluence retention SOP regardless of us.

What we owe them, and what must actually get built:

- **Sealed export before prune.** A date-bounded ledger segment, hash-sealed, attached to the Confluence dossier, attachment hash verified, and only then are the rows pruned. Each segment carries the prior segment's terminal hash, so the chain stays continuous across the boundary.
- **A retention SOP template** shipped with the app, naming what the customer must configure: Confluence space permissions, deletion controls, backup policy, retention period.
- **An honest limitation statement**: the app holds no legal-hold-protected copy. A user with sufficient Confluence permissions can delete the dossier. That risk is managed by access control and procedure, exactly as it is in every database-backed ALM tool including Codebeamer.

### The engineering instruction that follows

**Build the export step behind an interface.** `ExportTarget` with one implementation (`ConfluenceTarget`) in V1. If retention ever needs object-lock storage, adding `S3ObjectLockTarget` becomes a plug-in rather than a re-architecture — and that is also the migration path back to an external backend if the ALM ambition returns. This costs almost nothing now and preserves the option.

## 5. Build phases and effort

One experienced Forge developer. Estimates, not commitments.

| Phase | Work | Effort |
| --- | --- | --- |
| **0 · De-risk spike** | Measure validator latency against real Jira. Measure PBKDF2 600k in a Forge function. Prove concurrent ledger append on real Forge SQL. **Go/no-go on the gate design.** | 1 wk |
| **1 · Foundation** | Manifest, `sql` module, schema + migration runner, admin bootstrap, VA Admin seeding with minimum-count enforcement | 2 wks |
| **2 · Signing path** | TOTP enrolment (QR + confirm step), encrypted credential store, issue panel, `createSignature`, validator gate, content-hash staleness check | 3 wks |
| **3 · Compliance surface** | Hash-chained ledger + verification job, 3-attempt lockout, Jira-issue alerting, 90-day dead-credential check, self-service TOTP reset, My Signatures worklist, content-change review queue | 2.5 wks |
| **4 · Retention** | Sealed Confluence export + verified prune. Not deferrable — it is the 1 GiB answer. | 1.5 wks |
| **5 · Hardening & evidence** | Fail-closed test matrix, chain verification tool, Part 11 conformance matrix, tool qualification pack, Marketplace security review prep | 3 wks |

**≈ 13 weeks to a defensible V1**, plus Marketplace review turnaround.

Phase 0 is not a formality. If the latency budget fails, phases 1–5 are built on sand.

## 6. Fail-closed is the product

One rule outranks every other design consideration: **any error, anywhere in the gate path, blocks the transition.**

SQL timeout, key resolution failure, chain append exhaustion, malformed row, unexpected exception — all return `{ result: false }` with an honest message. There is no code path in this app that permits a transition it could not affirmatively verify.

A validator that fails open is not a bug. It is the product not working, silently, in exactly the circumstances an auditor will ask about.

## 7. Open items

**Must resolve in Phase 0**

- Jira workflow validator timeout — empirical, undocumented, and the design depends on it
- ~~PBKDF2 600k iteration cost inside a Forge function invocation budget~~ retired: TOTP verification is a single HMAC-SHA1, not a deliberately-slow KDF (§0b)
- App-level encrypted variable provisioning for the TOTP secret key (`forge variables set --encrypt`) — confirm it is set before first enrolment, and design the "not yet configured" failure path (fail closed: no key, no enrolment, not "enrol with a weaker fallback")
- TOTP clock-drift window (`TOTP_WINDOW = 1`, ±30s) sufficiency against real user devices — widen only if Phase 0 evidence shows genuine drift-caused failures, not speculatively
- Whether `write:jira-work` for security alerting AND rejected-change author notification passes the security review, given the app otherwise writes nothing

**Must resolve before launch**

- Break-glass override: an explicit, logged, time-boxed grant that the *consume* path reads. Never a branch in the validator, or the override is invisible to the chain.
- Confluence space and permission model for the audit dossier
- Retention SOP template drafted and reviewed with your first design partner — before build completes, not after
- Confirm no design partner is contractually required to hold legal-hold-capable storage (some pharma QMS agreements are)

**Girish**

- Runs on Atlassian eligibility is now a real, defensible packaging claim. It changes the pitch.

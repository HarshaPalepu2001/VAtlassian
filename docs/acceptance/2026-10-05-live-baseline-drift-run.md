## Action items (defects)

- **D1. Lozenge stale on children.** The Baseline status lozenge reads the stored review state (`va_item_state`,
  `src/resolvers/issueStatus.js`). After a link or a new child, the child's lozenge stays "Baselined" while its
  panel says DRIFTED; the root's lozenge is correct. Reproduced on VAT-44 (A4/A5) and VAT-45 (A6). Suspect: the
  link/updated triggers record drift for the tree root only. Also affects My approvals and the reconcile queue.
- **D2. WITHDRAWN 2026-10-06: re-versioning every child on a parent approval is accepted; the 2026-09-24 spec §4.1 stands and the code is right.** Original note: a parent approval re-versions children that did not change. Expected: only drifted or new children get a
  new version (user rule). Observed: VAT-45 v1 to v2 at E's approval in A5. The 2026-09-24 spec §4.1 says every
  child gets a version at every parent capture; the spec needs to change with the code.
- **D3. Approving a new child node at a child does not clear the root.** E's stored tree still lacks VAT-48 after
  VAT-45's own tree captured it. Expected: E's drift clears and its version stays. Observed: only a second,
  root-level approval cleared it (version bump).
- **Spec note.** Spec §4.3/§6 say a child's drift does not hold the parent. The app holds the parent (matches the
  user's expectation). Update the spec.
- **D1 still reproduces on 7.26.0.** On VAT-45 before A7's approval the sidebar lozenge read "Signed, Baseline version 4" while the panel said 2 changes need a decision. Also, E's sidebar said "1 change since approval" while its panel said 2 (probably the sidebar counts only the Epic's own field changes, not covered children; confirmed with B2: priority change plus child link read 1 in the sidebar and 2 in the panel).
- **D4. Restoring a never-set rich-text field leaves drift behind.** Baseline v7 of VAT-42 had no description (null). After the restore Jira holds an empty ADF document (`{type:doc,version:1,content:[]}`) and `normaliseAdf` (src/lib/content.js) hashes null and an empty document differently, so the app reports a Critical "document structure changed" on a field that has no content, shows "Partly restored", and a retry would produce the same result. Likely fix: treat an empty document as no value in the ADF normalisation and in the restore verifier, with a compatibility rule for stored hashes. Not caused by who wrote it: a PUT of `description: null` made as the user through the user's own Jira session returned 204 and Jira still read back the empty document, and VAT-42 stayed drifted. Jira keeps an empty document once a description has been set and cleared. FIXED in 7.27.0 (2026-10-06): an empty rich-text document now reads as no value (`isEmptyAdf`, `digestsEquivalent` in src/lib/content.js, used by the drift check, the restore verifier and the review diff); baselines stored from an empty document before the rule stay valid. New test/empty-adf-document.test.js (4 tests, watched failing first; its failing digests matched the production log), all 1676 tests pass. Live check on VAT-42 after deploy: "Matches baseline version 7, in sync", Changes since approval None, transition open. Still wrong on VAT-42: the stored restore status still reads "Partly restored" with a Retry restore button (it is not re-checked once drift clears), and the sidebar lozenge still reads Drifted "1 change since approval" (D1).

- **D8. "Restore as acting user" does not apply to tree restores (found by code reading, not yet shown live).** `restore.actAs` is read only by the single-issue executor (`src/lib/restore/executor.js`). The tree adapters (`src/lib/tree/restoreAdapters.js`) always use `api.asApp()` with the screen-security and editable-flag overrides, both for the permission preflight (`/mypermissions` is asked as the app) and every write. So a parent or child restore never runs as the signer, whatever Admin > Settings says, and a reviewer who cannot edit or even see a child still rewrites it by rejecting its parent. The "Restore identity" note below is true only for single-issue restores.
- **Restore identity.** The restore writes as the app by default (`restore.actAs: 'app'`, src/db/configStore.js); Admin > Settings > "Restore as" switches it to the acting user. As the user, the admin-only overrides (screen security, editable flag) are not sent, so fields hidden from the edit screen are not restorable by non-admins.

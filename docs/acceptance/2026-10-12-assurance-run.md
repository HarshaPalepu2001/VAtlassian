# Assurance run — 12 cases, one per promise — 2026-10-12

Goal: close the "does it hold?" question with few cases. Each case proves one or more of the
promises below, end to end, on the live tenant. Every action is recorded in the Results
table as it happens.

Tenant `mgtechdemo.atlassian.net`, project `VAT`, Forge `development`, app **8.9.0** (deployed 2026-10-12
17:28 UTC from the working tree: the 8.8.0 scope fix plus the hold and flag rule below). Fixture prefix
`LIVE-AS-20261012`.

## The promises (what the user said must hold)

| # | Promise |
|---|---|
| P1 | A parent's baseline covers the whole tree downward: every descendant (child, its child, …) with its controlled fields, its links and its sub-tasks. All get v1, signed by the parent's signature. |
| P2 | A link is recorded as link type + direction + the other issue's key. The linked issue's own fields are never recorded, and drift on one issue never touches the issue at the other end. |
| P3 | **The flag climbs, only upward:** a change anywhere asks every ancestor, up to the top parent, for a decision. No flag goes down. |
| P4 | A decision taken at any level covers that issue and everything below it, nothing above or beside it, and is signed with the assurance method of that level's latest baseline. |
| P5 | Approve = one new baseline for the decided subtree. Reject = the subtree goes back to its latest baseline, no new version. |
| P6 | Per-field decisions: rejected fields are restored first, then one new baseline is recorded. All approved ≡ Approve. All rejected ≡ Reject (no new version). |
| P7 | **The hold runs, only downward** (by Jira's parent field): a drifted issue cannot take any transition, and neither can anything below it. Its ancestors, siblings and linked issues are not held. An issue with no drift on itself or above it transitions normally under its controlled-transition rule, with no false alarm (user, 2026-10-12). |
| P8 | Every baselined attachment has a copy in the Forge Object Store, and a rejection brings back those exact bytes from it. |
| P9 | Rich text comes back exactly: deleting a whole description (with an embedded image) and rejecting returns the same content, the same media and the same placement. |

### Where the code is known to differ from the promises (read before running)

- **P3/P7 built for this run (app 8.9.0, deployed 2026-10-12 17:28 UTC, before T1).** Before it, a parent's
  drift held only the parent (`docs/specs/2026-09-24-child-baselines-design.md` §4.6/§6), and a Story
  captured by its Epic never saw its Sub-task's drift. Now `src/lib/ancestorHold.js` walks Jira's
  `parent` field upward and judges each ancestor on its own fields, with the same live check. It's used by
  the validator (`gate:deny ANCESTOR_DRIFT`, naming the ancestor), the signing step (refused before
  any challenge, so no authentication is spent), the transition-screen field and the panel ("Held:
  VAT-x, above this work item, …"). The middle-level flag counts the slice of the parent's signed tree
  under the child (`driftedDescendantsOfNode`). Tests: `test/validator-scenarios.test.js` S130 (rewritten
  on purpose), S138–S143; `test/approval-submit.test.js`; `test/panel-performance-contract.test.js`;
  `test/tree-storage.test.js`. Full verify passed: 1,700 backend tests, 253 UI tests, smoke and build.
- **P2 when both ends are baselined:** by the 2026-09-28 decision ("links have two owners"), a link
  change appears on both ends and one decision settles both. In this fixture L1 is never baselined,
  so P2 here means "L1's content is invisible to E's baseline".
- **P5 "don't touch the others":** a top-level approve gives every child a new version even when
  it did not change (accepted 2026-10-06). Siblings and ancestors of a lower-level decision must not
  change.
